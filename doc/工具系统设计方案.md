# 工具系统设计方案

## 1. 背景

当前 `agent-go/tool` 只有一个最小接口：

```go
type Tool interface {
	Name() string
	Description() string
	Execute(context.Context, []byte) ([]byte, error)
}
```

该接口可以执行工具，但无法表达模型需要的 JSON Schema、调用 ID、统一工具目录、执行元数据和可组合的执行策略。参考 `workspace/acore` 的 `ToolRuntime`、Builder、执行中间件和 Result Metadata 设计，本方案将工具系统拆分为注册、描述、解析、执行和观测几个职责明确的组件。

本方案只定义工具系统边界，不实现具体工具、JSON Schema 完整校验器或 Agent ToolLoop。

## 2. 目标与非目标

### 2.1 目标

- 让模型只看到稳定、可序列化的工具描述，不依赖具体 Tool 实现。
- 通过工具名安全解析模型的调用请求，并执行对应工具。
- 支持调用 ID、原始 JSON 参数和统一结果元数据。
- 通过 Builder 完成启动期注册和校验，构建后得到可并发使用的不可变 Runtime。
- 通过函数式 Middleware 扩展鉴权、审计、日志、限时、指标和限流能力。
- 保证 Tool 不共享调用方可变参数，支持 context 取消。
- 为 Agent 的 SingleTurn/ToolLoop 策略提供最小 `Service` 接口。

### 2.2 非目标

- ToolRuntime 不调用模型，也不决定模型何时执行 ToolLoop。
- 不在工具包中实现自动重试、熔断、全局限流或全局权限系统。
- 不在本阶段引入全局注册表、反射式自动发现或插件加载。
- 不把 provider 专属工具格式泄漏到公共 Tool 接口。
- 不默认执行任意 Shell、HTTP、文件系统或脚本能力。
- 不依赖第三方 JSON Schema 库；第一阶段只校验参数是 JSON object，完整 Schema 校验作为可替换扩展点。

## 3. 总体架构

```text
模型适配层
  └─ model ToolCall {ID, Name, Arguments}
       │ 适配
       ▼
Agent 运行策略 / ToolLoop
  └─ tool.Service
       │
       ▼
ToolRuntime
  ├─ 校验 Call
  ├─ 按名称解析注册工具
  ├─ 执行 Middleware 链
  ├─ 执行具体 Tool
  └─ 统一补充 ResultMetadata
       │
       ▼
具体 Tool 实现
```

依赖方向：

```text
agent ──> tool
model ──> message
tool  ──> 标准库
provider ──> model、tool（按适配需要）
tool 不依赖 agent、model 或 provider
```

`tool` 使用 `encoding/json.RawMessage` 表示参数和 Schema，避免与模型层形成循环依赖。运行策略把 `message.ContentToolCall` 转换成 `tool.Call`，再把 `tool.Result` 转换成 `message.RoleTool` 消息。

## 4. 核心数据模型

### 4.1 ToolSpec

```go
type Spec struct {
	Name        string          `json:"name"`
	Description string          `json:"description,omitempty"`
	Parameters  json.RawMessage `json:"parameters"`
}
```

`Parameters` 表示 JSON Schema，要求顶层是 JSON object。Schema 在注册时复制，`Specs()` 返回副本，调用方修改返回值不能影响 Runtime。

Tool 名称是 Runtime 内的唯一键，建议约束为非空、长度有限、只允许稳定的 ASCII 标识符，例如 `search_documents`。第一阶段可以只要求非空，以避免把命名规则过早固定；一旦对外暴露，应补充最大长度和字符集校验。

### 4.2 Tool Call

```go
type Call struct {
	ID        string          `json:"id,omitempty"`
	Name      string          `json:"name"`
	Arguments json.RawMessage `json:"arguments"`
}
```

`ID` 用于将模型产生的调用与 Tool 结果关联，可以为空以兼容不提供 ID 的调用方。`Arguments` 必须是 JSON object，Runtime 在进入 Middleware 和具体 Tool 前都应使用副本。

### 4.3 Tool Result

```go
type Result struct {
	Content  string         `json:"content"`
	Metadata ResultMetadata `json:"metadata"`
}

type ResultMetadata struct {
	CallID      string `json:"callId,omitempty"`
	ToolName    string `json:"toolName,omitempty"`
	StartTimeMS int64  `json:"startTimeMs"`
	EndTimeMS   int64  `json:"endTimeMs"`
	DurationMS  int64  `json:"durationMs"`
	Success     bool   `json:"success"`
}
```

Tool 只负责返回业务内容；Runtime 统一覆盖元数据，避免 Tool 伪造调用 ID、工具名或耗时。执行失败通过 `error` 返回，不使用 `Result.Success=false` 替代错误；这样 Agent 可以明确区分成功结果和执行失败。

第一阶段 `Content` 使用字符串，适合将 Tool 结果作为模型文本消息。若未来需要图片、结构化 JSON 或大文件引用，再引入独立 Result Content 类型，不直接把任意 `any` 放入结果。

## 5. 公开接口

### 5.1 Tool

```go
type Tool interface {
	Spec() Spec
	Execute(context.Context, json.RawMessage) (Result, error)
}
```

选择 `Spec()` 而不是 `Name()`、`Description()` 两个方法，是因为模型描述本质上是一个不可变快照，后续增加参数 Schema 或版本字段时不需要继续扩大接口。Tool 实例可被并发调用，必须自行保证内部状态安全，并尊重 context 取消。

### 5.2 Service

```go
type Service interface {
	Specs() []Spec
	Execute(context.Context, Call) (Result, error)
}
```

`Service` 是 Agent 使用方依赖的最小接口。Agent 不依赖 `Builder` 或 `ToolRuntime` 具体类型，因此可以使用内存实现、远程代理或测试替身。

### 5.3 Middleware

```go
type ExecuteNext func(context.Context, Call) (Result, error)

type ExecuteMiddleware func(
	context.Context,
	Call,
	ExecuteNext,
) (Result, error)
```

Middleware 按注册顺序进入、按逆序返回：

```text
Execute
  └─ Auth
      └─ Audit
          └─ Timeout
              └─ Tool
```

不调用 `next` 可以短路执行，例如权限拒绝或限流。Middleware 可以传递修改后的 Call，但不能修改调用方持有的原始参数。

Middleware 允许显式调用 `next` 多次，但每次都可能真正产生副作用。框架不自动重试，任何重试 Middleware 都必须自行处理次数、退避、幂等性和取消。

## 6. Builder 与 Runtime

```go
type Builder struct {
	// 私有工具目录、注册顺序、中间件和 built 状态
}

func NewBuilder() *Builder
func (b *Builder) AddTool(value Tool) error
func (b *Builder) AddMiddleware(value ExecuteMiddleware) error
func (b *Builder) Build() (*ToolRuntime, error)
```

Builder 只用于启动期单 goroutine 组装：

- 拒绝 nil Tool，包括 typed nil；
- 拒绝空工具名、非法 Schema 和重复名称；
- 拒绝 nil Middleware；
- 成功 Build 后冻结，后续 AddTool/AddMiddleware/Build 返回 `ErrBuilderBuilt`；
- Build 复制工具描述、中间件切片和注册顺序；
- Tool 实例本身不复制，Runtime 只要求其符合并发契约。

`ToolRuntime` 是不可变工具目录和执行服务：

```go
type ToolRuntime struct {
	// 私有 map[string]registeredTool、Spec 切片和 Middleware 切片
}

func (r *ToolRuntime) Specs() []Spec
func (r *ToolRuntime) Execute(context.Context, Call) (Result, error)
```

Runtime 不启动 goroutine，不保存单次调用状态，不依赖全局变量，可以被多个 Agent Run 并发使用。

## 7. 执行流程与错误契约

`Execute` 的顺序固定为：

1. 校验 context 非空且未取消。
2. 校验 Call 名称非空。
3. 校验 Arguments 是 JSON object。
4. 按名称查找工具。
5. 记录开始时间，构造 Middleware 链。
6. 执行 Middleware 和目标 Tool。
7. 成功时覆盖 ResultMetadata 并返回；失败时返回零值 Result 和包装后的错误。

建议定义以下稳定错误：

```go
ErrBuilderBuilt
ErrNilTool
ErrEmptyToolName
ErrInvalidSchema
ErrDuplicateTool
ErrNilExecuteMiddleware
ErrInvalidArguments
ErrToolNotFound
ErrInvalidResultMetadata
```

错误使用 `%w` 保留错误链，调用方通过 `errors.Is` 或 `errors.As` 判断类别。错误信息不得包含完整参数、密钥、Authorization、Cookie 或其他敏感内容；工具名可以包含在错误上下文中。

Middleware 和 Tool 的错误按执行层级包装，例如：

```go
return Result{}, fmt.Errorf("tool: execute %q: %w", call.Name, err)
```

不在 Runtime 内重复记录日志，日志、审计和指标由 Middleware 或上层统一负责。

## 8. 安全边界

### 参数安全

- 所有调用参数都来自外部模型输出，必须校验 JSON 格式和对象结构。
- Schema 完整校验应由独立 `ArgumentValidator` 扩展点承担，不能依赖 Tool 自己“顺便校验”。
- Tool 仍必须对业务字段做长度、范围、权限和资源限制校验。
- Runtime 不把参数原文写入日志；审计 Middleware 需要显式脱敏和大小限制。

### 执行安全

- 每个 Tool 必须通过 context 控制网络、文件和数据库等阻塞操作。
- 工具应有明确的超时、最大输出大小和资源消耗边界；默认超时由上层或 Timeout Middleware 注入。
- Shell、HTTP、文件系统等高风险工具不应作为通用内置能力自动注册。
- 权限判断放在 Middleware 或具体业务服务中，不能通过工具名约定替代授权。

### 输出安全

- Tool Result 不自动包含内部错误堆栈、文件路径、凭证或完整下游响应。
- 结果进入模型上下文前应执行大小限制和必要的敏感信息过滤。
- 失败统一走 error，避免让模型把失败详情误认为可信业务结果。

## 9. 与 Agent ToolLoop 的协作

ToolRuntime 只执行一次 Call，ToolLoop 负责流程编排：

```text
模型生成
  ├─ 无 ToolCall：结束运行
  └─ 有 ToolCall
       ├─ 校验调用数量和总轮数
       ├─ ToolRuntime.Execute
       ├─ 追加 assistant ToolCall 消息
       ├─ 追加 tool Result 消息
       └─ 再次调用模型
```

建议 ToolLoop 由 Agent 策略持有 `tool.Service`，而不是让 ToolRuntime 直接依赖 Agent。策略需要负责：

- 最大模型轮数；
- 单轮最大 ToolCall 数量；
- 是否串行或并行执行多个独立调用；
- ToolCall ID 与结果的对应关系；
- 工具失败后的终止、继续或转为错误消息策略；
- 将 Tool Result 写入 Session 的消息格式；
- 上下文裁剪和总 Token 预算。

第一阶段建议串行执行 ToolCall。只有确认工具之间无依赖、并发收益明确且 Session/事件顺序已有稳定定义后，再增加并行执行。并行执行时必须保持结果与 Call ID 的关联，并处理 context 取消和部分成功。

## 10. 包结构

```text
tool/
  doc.go
  tool.go                    # Spec、Call、Result、Tool、Service、Middleware
  builder.go                 # Builder、注册校验、构建冻结
  runtime.go                 # ToolRuntime 执行链
  result_metadata.go         # ResultMetadataBuilder（可选拆分）
  builder_test.go
  runtime_test.go
  example_test.go
```

不新增 `tool/registry`、`tool/manager` 或全局 `tool.System` 包。注册和执行属于同一个不可变 Runtime，避免目录与执行服务出现生命周期不一致。

## 11. 实施阶段

### 阶段一：基础契约和内存 Runtime

1. 将现有 `Tool` 从 `Name/Description/[]byte` 迁移为 `Spec/RawMessage`。
2. 新增 `Spec`、`Call`、`Result` 和 `ResultMetadata`。
3. 新增 Builder、ToolRuntime、Service 和稳定错误。
4. 实现工具名唯一、Schema object、参数 object 和深拷贝规则。
5. 完成静态、错误、并发和 Builder 冻结测试。

这是对当前公开 Tool 接口的破坏性调整。当前项目仍处于基础建设阶段，建议直接迁移，不保留旧接口别名；若已有外部调用方，再提供独立适配器而不是让 Runtime 同时支持两套接口。

### 阶段二：执行中间件和元数据

1. 增加函数式 Middleware 责任链。
2. 增加统一执行元数据和验证。
3. 补充鉴权、审计、超时、指标的示例 Middleware。
4. 明确错误包装和短路行为。

默认不内置具体鉴权、重试或限流策略，避免框架替应用做安全和可靠性决策。

### 阶段三：Agent ToolLoop 集成

1. Agent 策略通过 `tool.Service` 获取 Specs 和执行 Call。
2. 增加模型 ToolCall 到 `tool.Call` 的适配函数。
3. 增加 Tool Result 到 `message.RoleTool` 的转换。
4. 集成 Session、上下文裁剪和事件输出。
5. 默认串行 ToolLoop，后续按实际需求增加受控并发。

## 12. 测试与验收标准

### Builder/目录

- 空工具系统可以成功 Build。
- nil/typed nil Tool 被拒绝。
- 空名称、非法 Schema、重复名称被拒绝。
- Build 后 Builder 不可继续修改。
- Specs 按注册顺序返回，修改返回值不污染 Runtime。

### Runtime/执行

- 合法 Call 能解析并执行目标 Tool。
- 空名称、非法 JSON、非 object 参数和未知工具返回稳定错误。
- 传给 Tool 的参数与调用方隔离。
- context 取消会阻止执行或尽快传递给 Tool。
- Tool 错误和 Middleware 错误保留错误链。
- Result 内容保留，Metadata 的 CallID、ToolName、时间和耗时由 Runtime 统一生成。

### Middleware/并发

- Middleware 按注册顺序进入、逆序返回。
- Middleware 可以短路且短路时目标 Tool 不执行。
- Middleware 可以修改传给 next 的 Call，但不修改原始 Call。
- 多个 goroutine 并发 Execute 无数据竞争。
- 明确测试 Middleware 不应重复执行有副作用 Tool，除非调用方显式选择重试。

### 组合验收

- 模型 ToolCall 能正确转换为 Tool Call。
- Tool Result 能正确生成 Tool 消息，并保留 Call ID。
- ToolRuntime 不依赖 Agent、Model 或 Provider。
- 完成实现后执行：

```bash
gofmt -w <changed-go-files>
GOCACHE=/tmp/agent-go-gocache go test ./...
GOCACHE=/tmp/agent-go-gocache go vet ./...
CGO_ENABLED=1 GOCACHE=/tmp/agent-go-gocache go test -race ./...
```

如果测试环境没有 C 编译器，race 检查需要在具备 `gcc` 或等价工具链的环境执行。
